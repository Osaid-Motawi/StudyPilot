# Phase 0 Research: AI Study Companion (Four-Part Expansion)

**Feature**: 002-ai-study-companion | **Date**: 2026-07-24

Resolves the technical unknowns for extending StudyPilot into four parts. Builds on
the 001 research (uAgents REST, ASI:One structured output, Firebase token
verification, per-user isolation) which still holds.

## 1. ASI:One vision (image input) — does it exist? (KEY DECISION)

**Decision**: **No native vision.** Per current ASI:One documentation, the chat
completions API (`/v1/chat/completions`, models `asi1` / `asi1-mini` / `asi1-ultra`)
takes text message `content`; there is a separate **image *generation*** endpoint
(`/v1/image/generate`) but **no documented image *input* / multimodal vision**.
Therefore the agent will **OCR uploaded images to text** and keep the entire
downstream pipeline text-based (generation, chat, grading all operate on text).

**Rationale**: Keeps the constitution's "image analysis = agent" boundary while
using only capabilities ASI:One actually offers. Text-in means the existing
generation/grading/chat prompts and structured-output schemas are reused unchanged
for image-sourced material. If ASI:One adds vision later, only `agent/ocr.py` and
one prompt path change — the backend↔agent contract stays stable.

**Alternatives considered**:
- *Send images directly to ASI:One (vision)*: rejected — not supported per docs.
- *Backend-side OCR*: rejected — image understanding is the agent's responsibility
  (Principle II); PDFs/`.txt` stay in the backend extractor as today.

## 2. OCR engine for the agent

**Decision**: Use **Tesseract OCR via `pytesseract`** in the agent (`agent/ocr.py`),
behind a mockable function `image_to_text(image_bytes) -> str`.

**Rationale**: Lightweight Python binding, widely used, good enough for typed/clean
study images. Keeps dependencies minimal at runtime. The OCR function is a seam so
tests never need the binary.

**Prerequisite / tradeoff**: Tesseract must be installed on the host (documented in
quickstart). If OCR yields too little text, the agent returns the same
"insufficient material" signal used elsewhere.

**Alternatives considered**: `easyocr` (rejected — pulls PyTorch, heavy, against
minimal-stack); a cloud OCR API (rejected — new external dependency + cost).

## 3. Question types, generation, and scoring split

**Decision**: Each quiz is a single selected **question type**. Generation and
grading route as follows:

| Type | Generated by | Scored by | Method |
|------|--------------|-----------|--------|
| multiple-choice | agent | **backend** | deterministic: selected index vs `correctOptionIndex` |
| matching (3–10 pairs) | agent | **backend** | deterministic: count correct pairings |
| fill-in-the-blank | agent | **agent** | AI semantic correct/incorrect (reuse `/grade-short-answer`) |
| essay/free-response | agent | **agent** | AI numeric score (0–100) + written feedback (`/grade-essay`) |

**Rationale**: Matches constitution v1.2.0 — deterministic comparison in the
backend, judgment over free text in the agent. Reuses the existing short-answer
grader for fill-in-blank. `scorePercent` unifies mixed types for the Profile.

**Alternatives considered**: grading everything in the agent (rejected — wastes AI
calls and violates the deterministic-scoring boundary for mcq/matching).

## 4. General chat + multi-turn context (persisted)

**Decision**: The backend persists conversations at `users/{uid}/chats/{chatId}`
(ordered messages). On each user message the backend appends it, sends the recent
conversation history to the agent's `/chat` endpoint, appends the assistant reply,
and returns it. ASI:One is stateless per call, so the backend supplies history;
an optional `x-session-id` may be passed but is not relied upon.

**Rationale**: Satisfies persistence (FR-023a) with the existing Firestore
isolation pattern, keeps the agent stateless/testable, and supports multi-turn by
replaying history. Chats stay separate from the Profile's quiz list.

**Alternatives considered**: ephemeral chat (rejected — clarified as persisted);
relying solely on ASI:One session memory (rejected — not durable, not per-user
controlled).

## 5. File/Image Analysis page (chat mode vs quiz mode)

**Decision**: `POST /api/analysis` (multipart: `file`, `mode`, optional `question`
/ `questionType`). Backend validates the upload type, obtains text — PDFs/`.txt`
via the existing extractor, **images via the agent's OCR** — then:
- **chat mode**: creates (or continues) a chat grounded in the extracted content
  and returns the assistant reply (reuses chat persistence).
- **quiz mode**: generates a quiz of the requested type from the content and
  returns it (reuses the quiz pipeline; the quiz appears in Profile history).

**Rationale**: Maximizes reuse of the chat and quiz pipelines; the only new
primitive is "content grounding" (the extracted text becomes the chat's context or
the quiz's `sourceText`). Uploaded bytes are discarded after extraction.

**Alternatives considered**: a wholly separate analysis subsystem (rejected —
duplicates chat/quiz logic).

## 6. Profile aggregates

**Decision**: `GET /api/profile/overview` returns `{ averageScorePercent,
totalQuizzes }` computed server-side over the user's attempts; the per-quiz list
reuses `GET /api/attempts` (title, questionType, scorePercent, submittedAt) and
review reuses `GET /api/attempts/:id` (read-only). Empty state → zero/none.

**Rationale**: Server-side aggregation keeps the numbers authoritative and scoped
to `uid`; reuses existing attempt endpoints for the list + review.

**Alternatives considered**: client-side aggregation (rejected — duplicates logic,
less authoritative); a denormalized stats doc (rejected — premature for MVP scale).

## 7. Backend/agent contract shape for the new work

**Decision**: Extend `agentClient` and the agent REST surface with typed
request/response models per contracts/agent-api.md; extend the backend REST surface
per contracts/backend-api.md. Reuse the existing error model
(`{error:{code,message}}`) and status map (400/401/404/422/502/504).
